۰. خلاصه

این پروژه چیست؟
ما برای «پلیس همراه پلاس» یک سیستم ساختیم که صفحات اپ مثل وب‌سایت از سرور می‌آید — نه اینکه برای هر فرم جدا برنامه‌نویسی کنیم. مأمور اپ را باز می‌کند؛ صفحه‌ها از سرور لود می‌شود.

چه کارهایی انجام شد؟ (به زبان ساده)

  • بیش از ۲۰۰ صفحه طراحی و ساخت شد (ورود، استعلام، ثبت تخلف، تصادفات، گزارش، ...)
  • پلاگین Figma ساختیم — طراحی در Figma را خودکار به JSON تبدیل می‌کند (سرعت طراحی چند برابر)
  • اپ اندروید + موتور رندر UI + SDK اعلان + SDK دوربین + سرور uiManager
  • کار آفلاین: مأمور وسط فرم اینترنت قطع شود، بعداً ادامه می‌دهد
  • اعلان گشت: push می‌آید → مأمور فرم را پر می‌کند → ثبت می‌شود (۱۴۰۵)
  • امضا، نقشه، عکس، صدا، کروکی تصادف — همه داخل اپ
  • سرور کنترل می‌کند اپ کجا برود، چه چیزی نشان دهد، چه patchی بزند — بدون نسخه جدید APK

چرا R&D (تحقیق و توسعه) لازم بود؟
هیچ‌کدام از این‌ها «آماده و plug-and-play» نبود. برای هر بخش اول تحقیق کردیم، بعد پیاده کردیم: انتخاب معماری SDUI، قرارداد سرور-کلاینت، patch، Figma→JSON، push، نقشه، آفلاین، فرم داینامیک گشت، ...

زمان: فروردین ۱۴۰۴ تا تیر ۱۴۰۵ — اکثر کارها ۱۴۰۴، تکمیل‌ها ۱۴۰۵.

۱. معرفی پروژه

این پروژه اکوسیستم پلیس همراه پلاس (PhPlus) است: اپ اندروید میدانی، موتور SDUI (37 ماژول Gradle)، SDKهای Push و دوربین، schema/JSON builder، و سرور uiManager که UI را از راه دور کنترل می‌کند. معماری Server-Driven UI به این معناست که رابط کاربری از JSON ساخته می‌شود و به‌جای Layout جدا برای هر صفحه، UI از سرور یا DB محلی بارگذاری و رندر می‌گردد.

جریان اصلی رندر UI:
JSON → ساختار داده UI → View اندروید

توسعه این پروژه از فروردین ۱۴۰۴ آغاز شده و تا تیر ۱۴۰۵ (زمان تهیه این مستند) ادامه دارد. اکثر کارهای کلاینت در سال ۱۴۰۴ انجام شده و در سه ماه اخیر (فروردین تا تیر ۱۴۰۵) تمرکز بر تکمیل ماژول تصادفات، بهینه‌سازی عملکرد، و پیاده‌سازی سرور نوتیفیکیشن و گشت انتظامی بوده است.

برای این پروژه بیش از ۲۰۰ صفحه طراحی و پیاده‌سازی شده که طراحی UI آن‌ها توسط توسعه‌دهنده پروژه انجام شده و محتوای صفحات از سرور دریافت و در اپلیکیشن رندر می‌شوند.

🗺️ یکپارچگی نقشه و مسیریابی Mapbox برای نمایش موقعیت، مسیریابی، و انتخاب نقطه روی نقشه در فرآیندهای میدانی.

سرور — نوتیفیکیشن و گشت انتظامی ۱۴۰۵

در سال ۱۴۰۵، سمت سرور (uiManager) برای اتصال نوتیفیکیشن به جریان عملیاتی گشت انتظامی توسعه یافت. این بخش مکمل کارهای کلاینت است و اجازه می‌دهد مأمور بدون خروج از اپ، خبر را ببیند، فرم را پر کند و مرحله بعد را ادامه دهد.

  • NotificationDispatcherFacade — ساخت UI نوتیف گشت (خبر، فرم، یا هر دو) از روی داده Mongo
  • buildCustomFormJson — تبدیل JSON فرم سرویس گشت به موتور UI (تمپلیت notif/custom)
  • GashtCallService — ثبت فرم، ارسال به Gateway، ذخیره وضعیت، ساخت فرم بعدی
  • NotificationFormHelper — منطق مشترک parse و merge داده فرم
  • مدل NotificationPayload — نگهداری entity به‌روز فرم در Mongo
  • مسیر جدید Coordinator: phPlus/notifications/gashtCallService

۴. معماری کل پروژه (تمام لایه‌ها)

پروژه PhPlus فقط یک اپلیکیشن Android نیست — یک اکوسیستم SDUI است که از چند لایه تشکیل شده. اپلیکیشن میدانی (اپ PhPlus) بالاترین لایه است؛ زیر آن موتور رندر، schema، ابزار ساخت JSON، SDKهای جانبی، و سرور uiManager قرار دارند.

۵. ناوبری و کنترل سرور روی کلاینت

یکی از اصول کلیدی این پروژه این است که سرور فقط داده برنمی‌گرداند — رفتار UI را هم کنترل می‌کند. کلاینت یک «موتور اجرا» است؛ تصمیم «برو صفحه X»، «patch بزن»، «bottom sheet باز کن» از پاسخ coordinator می‌آید.

۵.۱ دو نوع ناوبری

نوعمکانیزمچه کسی تصمیم می‌گیرد
ناوبری محلیدستور://load_screen?screen=...JSON صفحه — از پیش طراحی شده
ناوبری سرور-محورپاسخ call_service با کلید nextسرور uiManager — runtime

۵.۲ فلو load_screen (کلاینت → کلاینت)

  1. کاربر روی element با action کلیک می‌کند
  2. ActionHandler authority load_screen را handle می‌کند
  3. ScreenNavigationStack.push(screen) — صفحه به stack اضافه می‌شود
  4. MehdiActivity جدید با intent.putExtra("json", screenKey) باز می‌شود
  5. JSON از Room DB با کلید screen خوانده و رندر می‌شود
  6. دکمه Back → ScreenNavigationStack.pop() → صفحه قبلی

هدف: ناوبری بین 200+ صفحه بدون Fragment/Activity جدا برای هر فرم.

۵.۳ فلو call_service (کلاینت → سرور → کلاینت)

  1. Action: دستور://call_service?path=inquiryVehicle&...
  2. Handler پارامترها را جمع می‌کند؛ @{variables} resolve می‌شوند
  3. MehdiActivity.onRequest() — enrich: phId, versionCode, imei, deviceModel
  4. POST {BASE_URL}CallService/coordinator با body Map<String,String>
  5. سرور business logic را اجرا و پاسخ flat map برمی‌گرداند
  6. MehdiActivity.setupObservers() کلیدهای رزرو شده را parse می‌کند

۱۵. سرور — نوتیفیکیشن و گشت انتظامی (۱۴۰۵)

این بخش کارهایی را توضیح می‌دهد که در سال ۱۴۰۵ در سمت سرور (uiManager) برای گشت انتظامی و نوتیفیکیشن انجام شده است. هدف اصلی این بود که نوتیفیکیشن فقط یک پیام نمایشی نباشد، بلکه یک جریان عملیاتی کامل باشد: نمایش خبر، ساخت فرم از روی داده سرویس، ثبت اطلاعات، و رفتن به مرحله بعد — همه از داخل همان مسیر SDUI که کلاینت از قبل دارد.

مزیت اصلی این کار: دیگر لازم نیست برای هر فرم گشت، صفحه جدا و کد مخصوص بنویسیم. سرویس گشت ساختار فرم را می‌فرستد؛ سرور آن را به UI تبدیل می‌کند و کلاینت فقط رندر می‌کند. تغییر فیلد یا فرم جدید، سریع‌تر و با هزینه کمتر انجام می‌شود.

۱۳.۱ مشکل قبلی و راه‌حل

قبلاً برای هر سناریوی گشت، باید صفحه و منطق جدا تعریف می‌شد. اگر سرویس گشت فیلد جدید اضافه می‌کرد یا فرم چندمرحله‌ای می‌شد، تغییر در اپ و بک‌اند زمان‌بر بود. با پیاده‌سازی فرم داینامیک در سرور، این وابستگی کم شد و نوتیفیکیشن به یک ابزار عملیاتی واقعی تبدیل شد.
